Восстановление сессий за один проход

Разбор перед доработкой moku-rails checkpoint / resume-checkpoint · 6 ноября 2026 · Claude Code 2.1.317 · на машине только чтение, секреты и Keychain не трогались

Вывод. Почти всё делается официальными средствами: список сессий, команды продолжения, названия, рассылка новых id и копии артефактов. Недокументированная запись нужна только для двух вещей: открыть сессии в приложении без ручного запуска и вернуть вложенность в боковой панели. Обе вынесены в отдельные флаги, которые запускает человек.

Официальные средства делаем по умолчанию

  • Транскрипты и claude --resume <id>. Транскрипты не привязаны к аккаунту, разговор продолжается целиком.
  • Инструменты приложения из сессии: set_session_title возвращает название, send_message рассылает новые id. Из moku-rails их не вызвать, это обычная команда. Поэтому resume-checkpoint печатает готовые вызовы, а проводник moku выполняет их в своей сессии.
  • Только чтение индекса приложения (claude-code-sessions/<account>/<org>/local_*.json): поля isArchived, title, spawnedFrom, cliSessionId. Текущий аккаунт берём из переменных сессии CLAUDE_CODE_ACCOUNT_UUID и CLAUDE_CODE_ORGANIZATION_UUID. Если их нет, берём папку с самой свежей записью. .claude.json и токены не читаются.
  • Артефакты. В транскрипте есть вызовы Artifact (publish) с file_path, files и ссылкой в ответе. Исходные файлы копируются в чекпойнт. Если файла уже нет, последняя версия собирается из Write и следующих за ним Edit в том же транскрипте.
  • Без поля «родитель». Вложенность можно частично заменить официальными группами боковой панели (create_group, move_sessions). Это не та же иерархия, но риска нет.

Недокументированное только отдельным флагом

ДействиеРискЗащита
--open: script -q /dev/null claude --desktop --resume <id> </dev/null, по одной сессии, пауза 3 сСама команда официальная, обходной путь только в подмене терминала. При повторном запуске могут появиться дубли. Поведение без TTY может поменяться.Пропускаем сессии, которые уже открыты под новым аккаунтом (есть local_<id>.json). Запускает человек в своём терминале.
--relink: запись spawnedFrom (и title) в json приложения по карте «старый → новый», любая глубинаФормат никем не обещан и может смениться. Приложение держит записи в памяти и само их переписывает: 6 ноября файлы сессий без активности переписывались в 06:48 и 06:51. Правка, сделанная при открытом приложении, может пропасть.Команда отказывается работать, если приложение запущено. Перед правкой копирует каждую запись в <чекпойнт>/desktop-backup/. Меняет только два поля и проверяет, что json разбирается. Человек запускает команду сам и потом открывает приложение.

В ручном переезде правка при открытом приложении пережила перезапуск. Это одно наблюдение, а не гарантия, поэтому флаг всё равно требует закрытого приложения.

Как будет выглядеть переезд

  1. До смены входа: moku-rails checkpoint. Сохраняет живые сессии текущего аккаунта (id, старый local_, название, родителя, папку, ветку, станцию, фоновые задачи) и копии артефактов в ~/.claude/moku-checkpoints/<время>/.
  2. Человек сам входит в новый аккаунт (claude auth login или приложение).
  3. moku-rails resume-checkpoint --open в терминале при открытом приложении. Открывает все сессии.
  4. moku-rails resume-checkpoint в сессии проводника. Печатает карту id, вызовы set_session_title и сообщения родителям и самим сессиям (новые id детей, список артефактов с путями к копиям). Проводник отправляет их сам.
  5. Если нужна вложенность в панели: закрыть приложение, выполнить moku-rails resume-checkpoint --relink, открыть приложение.

Что не делаем

  • Не входим и не выходим из аккаунта сами, не читаем токены, .credentials.json и Keychain.
  • Не копируем все артефакты аккаунта, только опубликованные самой сессией.
  • Не трогаем записи старого аккаунта: они нужны как источник и остаются как есть.
